### 2.1 เหตุผลของแต่ละแถว

**TR-01 · เหตุใดเป็น Partially Supported**
- Fact: ตารางที่ 3.20 ข้อ 2 ให้ FE-2 "รับไฟล์ภาพและวิดีโอ พร้อมตรวจสอบประเภทและขนาดก่อนส่ง" และตารางที่ 3.23 ข้อ 5 ให้ตรวจ "ทั้ง MIME Type และ Magic Bytes" · §3.7.1 ระบุเงื่อนไข "เกิน 100 MB หรือประเภทไฟล์ไม่รองรับ"
- Fact: บทที่3 ไม่มีรายการประเภทไฟล์ที่รองรับ ขณะที่ SRS ข้อจำกัดข้อ 1 ระบุ JPG, PNG, MP4, MOV, AVI และ SE02 §11.2.2 ระบุ .jpg .png .mp4
- Missing Evidence: §3.7.2 ข้อ 2 บอกว่า Frontend "ส่ง HTTP POST พร้อม FormData ไปยัง Backend API" แต่ไม่ระบุ endpoint และไม่ระบุสิ่งที่ BE-2 ตอบกลับเมื่อไฟล์ไม่เข้าเงื่อนไข
- ข้อสรุป: มีส่วนประกอบรับผิดชอบครบทั้งสองชั้น แต่ขาดรายละเอียดที่ใช้ตั้งผลที่คาดหวัง จึงเป็น Partially ไม่ใช่ Not Supported

**TR-02 · เหตุใดเป็น Partially Supported**
- Fact: §3.4.3 แบ่ง Training/Validation/Testing 70/15/15 แบบ Video-level และ §3.11.3 กำหนด MT-01 Accuracy ≥ 90%, MT-02 AUC ≥ 0.95 บน Testing Set
- Fact: §3.4.5 ขยายกรอบใบหน้า "เพิ่มอีก 35% ในทุกทิศทาง" ขณะที่ SRS FR-005 และ SE02 §11.2.3 ระบุ "1.3 เท่า"
- Inference: ถ้าตอนใช้งานจริงขยายกรอบต่างจากตอนเทรน ภาพที่เข้าโมเดลจะต่างจากที่โมเดลเรียนรู้ ผลบน Testing Set จะไม่แทนผลจริง
- ข้อสรุป: วิธีวัดชัด แต่ค่าพารามิเตอร์ของ preprocessing ขัดกันระหว่างเอกสาร จึงรองรับได้บางส่วน

**TR-03 · เหตุใดเป็น Not Verifiable**
- Fact: ตารางที่ 3.21 ข้อ 3 บอกเพียงว่า BE-3 "ประสาน Pipeline ตรวจจับตั้งแต่แยกเฟรมถึง Inference" และ §3.7.2 ข้อ 6 บอกว่าผลถูกบันทึกลง FrameResult
- Missing Evidence: ไม่มีข้อใดในบทที่3 บอกวิธีรวมคะแนนของหลายเฟรมเป็นผลระดับวิดีโอ หรือค่า threshold ที่ใช้ตัดสิน Real/Fake
- ข้อสรุป: เอกสารไม่ได้บอกว่าไม่ทำ แต่ไม่ได้พูดถึง ทีมจึงตัดสินไม่ได้ และตั้ง DQ-05 แทนการเดา

**TR-04 · เหตุใดเป็น Not Supported**
- Fact: SRS FR-009 ต้องการ "ระดับความเสี่ยง (Low/Medium/High)" และ FR-008 ใช้คำว่า Risk Score
- Fact: ตารางที่ 3.20 ข้อ 3 และ §3.11.4 ออกแบบ FE-3 ให้แสดงป้าย REAL/FAKE กับ Confidence Score เป็นเปอร์เซ็นต์ และ Timeline Chart ไม่มีการแบ่งระดับความเสี่ยง
- Inference: "Confidence" กับ "Risk" มีความหมายต่างกัน ผู้ใช้อาจอ่าน Confidence 80% ของผล REAL ว่าเสี่ยง 80%
- ข้อสรุป: การออกแบบเลือกรูปแบบการแสดงผลที่ต่างจากที่ SRS กำหนดไว้ตรง ๆ จึงเป็น Not Supported · ทีมไม่ตัดสินว่าฉบับใดถูก บันทึกเป็น DQ-05

**TR-05 · ตัวเทียบของแถวที่รองรับ**
- Fact: ตารางที่ 3.23 ข้อ 3 ตรวจบทบาทใน JWT Payload "ก่อนทุก API Request" และ §3.10 แยกสิทธิ์ Guest / Member / Admin ตรงกับ SE02 §11.1
- ข้อควรระวัง: SRS ข้อจำกัดด้านขอบเขตข้อ 4 เขียนว่า "รองรับผู้ใช้งานในรูปแบบ User เดียว โดยไม่มีการแบ่งบทบาท Admin/Editor" ขัดกับ SE02 และบทที่3 · การออกแบบรองรับ SE02 ได้ แต่ต้องยืนยันว่า baseline คือฉบับใด (DQ-06)

**TR-06 · รองรับ แต่ยังมีความเสี่ยงต่อการทดสอบ**
- Fact: ตารางที่ 3.22 กำหนด path และระยะเวลาเก็บของแต่ละกลุ่มไฟล์ และใช้ R2 lifecycle ลบอัตโนมัติ
- Missing Evidence: แผนทดสอบ §3.11.5 (ST-01–ST-06) ไม่มีกรณีตรวจการลบไฟล์ตามระยะเวลา

**TR-07 · เหตุใดเป็น Not Verifiable**
- Fact: SRS NFR-002 ให้ภาพ ≤ 30 วินาที วิดีโอ ≤ 5 นาที · บทที่3 มีเพียง MT-05 Inference ≤ 500 ms ต่อภาพ และ §3.3 ระบุ Docker/Uvicorn โดยไม่ระบุทรัพยากรเครื่อง
- Missing Evidence: ไม่มีส่วนประกอบหรือข้อตัดสินใจใดเรื่องการประมวลผลแบบรอผล (synchronous) หรือคิวงาน และไม่มีขีดจำกัดเวลาของคำขอ
